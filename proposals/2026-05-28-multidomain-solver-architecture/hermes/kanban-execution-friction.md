# Hermes Kanban Execution Friction Report

Observed during autonomous execution of the `circuit-solver-gamma` board
(88 plan cards, 29 tasks × impl→review→integrate, 10 conflict-resolver cards).
Each item is classified by scope and includes the specific remediation needed in
upstream scientia or Hermes.

---

## CRITICAL — Affects every emit

### F-1: `apply()` creates cards before wiring parent links — dispatcher races ahead

**Symptom.** The `scientia.hermes.apply.apply()` function creates all cards in
topological order, then wires parent links in a second pass. The Hermes daemon
dispatches `ready` cards immediately. Every card with parents was created as
`ready` with `parents=[]`; the daemon claimed integrate cards before the
`review→integrate` link existed. Result: integrators ran with no gate, operated
on incomplete data, and produced spurious conflict-resolver cards.

**Evidence.** Event log on `t_fe8a9a07` (integrate #1):
```
[19:49] created {status: ready, parents: []}
[19:49] claimed, spawned                      ← dispatcher grabbed it
[19:50] linked {parent: t_8f7fe7e8}           ← 60s too late
```

**Root fix (scientia.hermes.apply).** At card-creation time, look up already-known
parent hermes IDs (guaranteed available because topological order means parents
are created first) and pass them via `--parent <id>` to `hermes kanban create`.
Cards with parents start as `blocked`; the dispatcher cannot claim them until all
parents are `done`. Eliminate the separate `POST /links` pass — parents wired at
creation are sufficient for dependency gating.

**Workaround applied.** Replaced `apply()` with a custom `_emit()` loop in
`hermes/emit.py` (v2) that passes `--parent` at creation time.

### F-2: Conflict-resolver cards created with blocked-integrate as parent — systematic deadlock

**Symptom.** When an integrator cannot merge, it calls `kanban_complete()` (or
`kanban_block()`) and creates a child card assigned to `conflict-resolver`. It
sets `parents=[<integrate_card_id>]` on the child. Because the integrate card is
`blocked` (never reaches `done`), the child stays in `todo` forever — a deadlock.

**Evidence.** Card `t_37fc896c` (conflict-resolver for integrate #1):
```yaml
created: {status: todo, parents: [t_fe8a9a07]}
# t_fe8a9a07 is blocked; resolver never becomes ready
```
Observed on tasks #1, #4, #5, #6, #11, #13, #14, #22 — every integrator that
spawned a resolver card reproduced this.

**Root fix (integrator SOUL / pipeline design).** Two options:
1. *Recommended.* Integrator reassigns its OWN card to `conflict-resolver` (no
   new card created). When the resolver calls `kanban_complete()` on the integrate
   card, downstream cards unblock normally. This is how `t_8bf5de98` (integrate
   #4) worked correctly after reassign.
2. If a separate child card is preferred, it must be created with NO parent link
   to the blocked integrate. The resolver then calls `kanban_complete()` on the
   integrate card explicitly after merging.

**Workaround applied.** Sweep script (`/tmp/kanban_sweep.sh`) polled for done
conflict-resolver cards and manually called `hermes kanban unblock <integrate_id>`
every 30 s.

### F-3: Integrator SOUL does not name the trunk branch — wrong-repo merges

**Symptom.** The integrator SOUL says "merge to trunk" without naming the branch.
In a git-worktree setup with multiple linked worktrees (`beta`, `gamma`, `main`),
the integrator resolves "trunk" from the parent directory of its worktree — which
depends entirely on where the Hermes daemon was started. When the daemon ran from
`circuit_solver.beta`, integrators merged into `beta` instead of `gamma`.

**Evidence.** Integrate #1's conflict description: *"Trunk (target): `beta` |
SHA `e5d33e6`"*. The emit had captured `base_sha = 2a430c0` (gamma HEAD), but
the integrator targeted beta, producing a false conflict.

**Root fix (SOUL template for integrator).** The SOUL.md template must include
a project-specific `## Critical: trunk branch is <X>` section generated by
`scientia-hermes-init` from the project's config/ADRs. The git branch name must
be explicit:
```
git checkout <trunk-branch>   # always; never infer from cwd
git merge <worker-branch>
```
`scientia-hermes-init` already has access to the project name and can derive the
trunk branch. The `soul-integrator` template should accept a `trunk_branch`
variable.

**Workaround applied.** Manually added the `## Critical: trunk branch is gamma`
section to both integrator and conflict-resolver SOULs and redeployed profiles.

## HIGH — Affects emit tooling on Hermes v0.15.x

### F-4: `scientia.hermes.apply._cli_transport()` calls `hermes kanban task create` — missing verb

**Symptom.** Hermes v0.15.1 removed the `task` subcommand; the working verb is
`hermes kanban create`. The scientia 1.0.0 `_cli_transport()` uses
`hermes kanban task create`, which exits with "invalid choice: task". The
`_rest_transport()` sends no Authorization header and receives `401` from the
dashboard. Both built-in transports are broken against v0.15.1.

**Root fix (scientia.hermes.apply).** Update `_cli_transport()` to use
`hermes kanban create <title> --body ... --idempotency-key ...` (positional title,
no `task` subcommand). Also update the link call: v0.15.1 uses positional args
`hermes kanban link <parent_id> <child_id>`, not `--parent/--child` flags.
Archive call: `hermes kanban archive <id>` (unchanged).

**Workaround applied.** Custom `_emit()` loop in `hermes/emit.py` using the
correct v0.15.1 CLI surface.

---

### F-5: `hermes kanban create --body @<file>` does not expand file references

**Symptom.** Card bodies are long markdown strings. Passing `--body @/tmp/body.md`
does not expand the file reference; the literal string `@/tmp/body.md` becomes
the body text.

**Root fix (hermes or scientia).** Either: (a) Hermes should support `@file`
expansion in `--body`, or (b) scientia's CLI shim should read the file and pass
the content as a literal string. Option (b) is already the correct workaround.

## MEDIUM — Agent discipline / self-block pattern

### F-6: Implementers self-block with "review-required" when tests pass

**Symptom.** Several impl agents called `kanban_block(reason="review-required: X
tests pass, needs eyes on...")` instead of `kanban_complete()`. The pipeline has
a dedicated reviewer stage; impl agents must never self-block for review. Tests
passing is the completion criterion.

**Evidence.** Blocked reasons on `t_df66b55d` (impl #25), `t_d0af001a` (impl
#11), `t_9c00ffba` (impl #19), `t_2c4c8595` (impl #29): all cited passing tests
plus a desire for human review.

**Root fix (implementer SOUL).** Strengthen the existing instruction. Current:
"do not self-block for review". Suggested replacement:
> **If `cargo test` passes and clippy is clean: call `kanban_complete()`.
> Do NOT call `kanban_block()`. The reviewer stage runs automatically — you do
> not control when it starts. Blocking here stalls the entire pipeline.**

**Workaround applied.** Sweep script pattern-matched "review-required" / "tests
pass" in block reasons and auto-unblocked.

---

### F-7: Reviewer self-blocks instead of completing with rejection

**Symptom.** When a reviewer finds a wrong implementation branch (old content,
missing files), it calls `kanban_block()` rather than `kanban_complete()` with a
rejection summary. This leaves the card blocked permanently since there is no
automatic re-dispatch path from reviewer-blocked.

**Root fix (reviewer SOUL).** Add an explicit rejection path:
> If the branch content is wrong or missing, `kanban_complete(summary="REJECTED:
> <reason>", metadata={...})`. Do not block — the integrator and conflict-resolver
> stages handle downstream failure. A completion with a REJECTED summary is
> preferable to a block that stalls the pipeline.

## MEDIUM — Git worktree environment

### F-8: Daemon `cwd` determines ALL task worktree base paths — not reset on reclaim

**Symptom.** Hermes creates task worktrees at `<daemon_cwd>/.worktrees/<task_id>`.
This path is stored in the card at first dispatch and is NOT reset on reclaim.
Restarting the daemon from a different directory does not re-home existing cards.
Integrators running in a beta worktree target beta's checked-out branch as trunk.

**Root fix (hermes or scientia-hermes-init).** Two options:
1. *Hermes.* Make the worktree base a per-board config (`kanban.boards.<slug>.
   worktree_base`) rather than daemon cwd.
2. *scientia.* Document that the daemon must be started from the correct repo.
   Add a `preflight` check: verify that the daemon's reported cwd matches the
   project root before emitting.

**Workaround applied.** Killed the beta daemon; started a new daemon with
`cd <gamma-repo> && hermes kanban --board <board> daemon ...`. Confirmed with
`ls -la /proc/<pid>/cwd`.

---

### F-9: Shared git worktrees with matching branch names — old content on task branches

**Symptom.** When a project has multiple linked worktrees (`beta`, `gamma`) and
both ran the same change against different bases, task branches like
`2026-05-28-multidomain-solver-architecture/task-6` exist in both with different
content. Impl agents dispatched against the gamma board found an existing branch
and used old beta content instead of implementing from the gamma base.

Affected tasks: #6, #8, #12, #14 (all had wrong branch content from beta
board's prior execution).

**Root fix (hermes / impl SOUL).** Two options:
1. *Hermes.* Include `base_sha` in the card and instruct the agent to reset the
   branch: `git branch -f <branch> <base_sha>` before starting work.
2. *SOUL.* Explicit instruction: "Before starting, reset your branch to `base_sha`
   regardless of whether the branch already exists: `git checkout -B <branch>
   <base_sha>`." This makes impl idempotent against stale branches.

## LOW — Monitoring / tooling

### F-10: Sweep script requires manual maintenance of resolver→integrate pairs

**Symptom.** The `check_pair(resolver_id, integrate_id)` logic in the sweep
script required hardcoding specific card IDs. A generic scan for done
conflict-resolver cards with blocked parents was needed but the grep pattern
(`conflict-resolver.*done` vs `done.*conflict-resolver`) was wrong.

**Root fix (scientia-hermes-status skill).** `scientia-hermes-status` should
expose a command that lists done resolver cards whose parent cards are still
blocked, and provides one-click unblock. This is a known operator action that
should not require a custom sweep script.

---

### F-11: `scientia.hermes.ledger` reports `created=0` after successful emit

**Symptom.** The reporting code in `emit.py` calls `ledger.load()` AFTER
`apply()` has written the new ledger. The `diff(old, plan)` then shows
`added=0` since `old` IS the new state. The emit succeeded (96 cards on the
board) but the script reported `created=0, existing=88`.

**Root fix (emit.py / scientia).** Load `old = ledger.load(change_id)` BEFORE
calling `apply()`/`_emit()`, then diff against the pre-emit snapshot.
